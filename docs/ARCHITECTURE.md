# Architecture

Live2D Viewer is an MVP with two native rendering paths behind one Flutter UI.
The architecture is deliberately boring: Flutter owns navigation and user
state, Rust owns model evaluation and GPU rendering, and a thin generated
bridge moves control calls and frame events across the boundary.

## Components

| Layer | Location | Responsibility |
| --- | --- | --- |
| Flutter shell | `app/lib/` | Pages, Riverpod state, settings, model discovery, remote downloads |
| FRB bridge | `app/lib/src/rust/`, `crates/mocari_host/src/frb_api.rs` | Generated Dart bindings and `RendererHandle` control surface |
| Host runtime | `crates/mocari_host/src/` | Model loading, gestures, fitting, frame loop, platform surfaces |
| Model runtime | `third_party/mocari/` | Cubism-compatible parsing, motion/physics evaluation, mesh generation |
| GPU renderer | `crates/mocari_host/src/render/`, Mocari's wgpu backend | Two-pass mask/model rendering |
| Remote catalog | `server/` | Generates `pkg-index/v1` and serves ZIP packages |

## Data flow

1. `LocalModelRepo` scans the app-managed directory and custom paths for
   `manifest.json` or `*.model3.json`.
2. `ModelNotifier` exposes the list to the Library. Selecting a model stores
   its path and the Viewer calls `RendererHandle.loadModel`.
3. Rust validates textures before handing the model to Mocari, builds GPU
   resources, and starts the platform frame loop.
4. Each tick evaluates motions/physics, updates meshes, renders the mask pass,
   renders the model pass, and presents or copies the frame.
5. Flutter receives a `FrameEvent.updated` with a texture id/handle and paints
   it with `Texture`.

## Windows path

- Flutter's Windows runner registers a GPU surface texture through
  `app/windows/runner/texture_handler.cpp`.
- Rust creates a D3D12 shared texture with
  `HEAP_FLAG_SHARED | ALLOW_SIMULTANEOUS_ACCESS` in
  `crates/mocari_host/src/render/shared_offscreen.rs`.
- The two render passes write to a **private** texture. A single
  `copy_texture_to_texture` copies the result into the shared resource.
- The runner hands the NT handle to Flutter as a `DxgiSharedHandle`.
- On resize, Rust creates a new shared resource. Flutter must swap the NT
  handle through the texture channel's `update` method while keeping the same
  Flutter texture id. Do **not** unregister/register during a resize.

## Android path

- `MainActivity.kt` creates a Flutter `SurfaceTexture`, converts its `Surface`
  to an `ANativeWindow*` through JNI, and passes the pointer to Rust.
- Rust creates a wgpu Vulkan surface from the native window and renders
  directly to it.
- `_createAndroidSurface`, `startFrameLoop`, `stopFrameLoop`, and
  `reattachAndroidSurface` are serialized through `_lifecycleChain` in
  `app/lib/providers/renderer_provider.dart`.
- Replacing the wgpu device during `install_android_surface` requires clearing
  `stage` and `offscreen_texture` before the swap; the caller must reload the
  model immediately afterwards.
- Android render buffers cap their long edge at 1600px before being handed to
  Kotlin and Rust. Gesture deltas still use unscaled surface coordinates.

## Frame loop invariants

These invariants are non-negotiable; they were established by the postmortems
in `docs/postmortem/`.

1. Acquire a frame, encode both passes, submit, then present (or copy) and
   schedule the next tick.
2. The mask pass runs before the model pass, with Mocari's clipping resources.
3. The shared Windows texture is never written by multiple draw calls
   directly. Render to the private target and copy atomically.
4. `FrameEvent.updated` may only be emitted after the GPU copy fence for that
   frame has retired. The production loop may wait outside the renderer lock,
   but never emits `Updated` before the wait succeeds.
5. `SharedOffscreenTexture` keeps a `wgpu::Device` clone in its **last** field
   so the manually-created D3D12 resource cannot outlive the device.
6. `load_model` runs texture preflight before Mocari decoding: PNG signature,
   dimensions, and decoded-memory budget.
7. wgpu uncaptured errors are logged, not panicked. Device creation goes
   through `RenderContext::request_device`.
8. Android device swaps clear the old stage/offscreen resources before any
   frame loop can render with them.
9. Frame-loop lifecycle operations are serialized. Use the `_xxxInner`
   variants inside the chain to avoid self-deadlock.

## Bridge and generated files

`crates/mocari_host/src/frb_api.rs` is the public control surface.
`crates/mocari_host/src/frb_generated.rs` and `app/lib/src/rust/**` are
generated by flutter_rust_bridge 2.9.0. Change the API, regenerate, and commit
the generated diff; do not hand-edit generated files.

`RendererHandle` is wrapped in `Arc<Mutex<Live2dRenderer>>`. Gesture state has
its own `GestureSlot` so high-frequency pan/zoom calls do not queue behind a
frame render. The frame loop and one-shot render methods share the same
renderer but differ in where they wait for GPU completion.

## Settings and model sources

- Settings live in a JSON file under the app support directory and are written
  with a temp-file rename. Writes are debounced; callers that need durability
  should await `save()`/`flush()` and handle errors.
- The app-managed model root is `.../live2d-viewer/models/`.
- Remote installs write `live2d-viewer.install-meta/v1` into the extracted
  directory **before** the atomic rename.
- Custom paths are scanned asynchronously because Android's FUSE storage does
  not reliably support synchronous directory scans.

## Renderer and dependency boundaries

- Keep platform-specific code behind `cfg(target_os = ...)`.
- Keep the vendored Mocari patch intact. The local modifications and upgrade
  checklist are in `third_party/mocari/UPSTREAM.md`.
- Do not reintroduce the removed built-in model extraction or a fake bundled
  sample. Test models are supplied through environment variables.
